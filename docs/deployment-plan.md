# Local and AWS deployment plan

The [local backend](local-backend.md) is implemented with Compose and LocalStack. No AWS infrastructure is provisioned; the AWS sections remain a deployment plan. Phase 1 pins Java 21, Spring Boot 3.5.16, AWS SDK 2.41.21, and KCL 3.4.3. The latest patch of the Boot 3.5 line was chosen to use its Jackson 2 integration alongside KCL; this is not a claim that it is the newest Spring Boot major. React/TypeScript remains planned. Maven dependencies and container digests are pinned in build files.

## Local environment

Docker Compose starts LocalStack (Kinesis and DynamoDB) and two backend containers. A LocalStack ready hook creates the stream, application tables, and TTL settings idempotently; KCL creates its own metadata tables when the consumer starts; it is tooling, not another service. A readiness dependency waits for initialization. The Phase 1 smoke script is an explicit host task. React and a load generator are not implemented. Bind host ports only on loopback. Persist emulator data in a named volume, with an explicit destructive reset command later documented separately.

Run the same AWS SDK/KCL and processing code in local and AWS modes. Configuration supplies `AWS_REGION`, optional Kinesis/DynamoDB endpoint overrides, stream name, three application table names, KCL application/metadata table names, dataset ID, fixed stripe count, CORS origins, HTTP limits, and log level. Metrics publication can be disabled locally without replacing processing logic. Fail startup on missing/invalid settings or inconsistent stripe count; never fall back from a failed local endpoint to a real AWS endpoint.

The optional `.env.example` contains placeholders only. Actual local `.env` values use non-secret emulator credentials, confined to Compose configuration; local tools against AWS use normal SDK providers, including short-lived environment credentials exported by the AWS CLI after SSO login; native SDK SSO modules are not included in the Phase 1 dependency set. No static credentials in Java, browser bundles, Dockerfiles, or repository files. Containers use `http://localstack:4566` internally; host tooling uses its loopback mapping. The browser calls backend HTTP ports, never AWS directly.

LocalStack 4.14.0 is pinned by digest and tested with KCL 3.x polling and DynamoDB transactions. Compose explicitly selects KCL’s built-in Linux CPU metric (`KCL_WORKER_METRIC=LINUX_CPU`), avoiding cloud metadata discovery. KCL still owns leases/checkpoints and retains its coordination tables. AWS defaults use `AUTO` discovery. The metric measures VM-wide CPU in this local setup; it is not a container capacity guarantee. The `THROUGHPUT` mode is used only by fresh-resource host integration tests: in KCL 3.4.3 it can stall idle lease recovery when zero throughput produces NaN, so it must not be used for the long-running local demo. CloudWatch publishing is disabled locally; no CloudWatch emulator is required. Emulation is not proof of IAM, leases under AWS failures, throughput, TLS, or AWS throttling behavior. A short disposable AWS test is required later for those properties. Do not switch to an in-memory consumer when emulation reveals a gap; document/fix compatibility or run that test in AWS.

## AWS topology

Use one region, one ECS cluster, two ECS services backed by separate ECR images, one Kinesis stream, three application DynamoDB tables, KCL metadata tables, and CloudWatch. Start with one Fargate task per service; initial task allocation is 1 vCPU / 2 GiB each, a sizing hypothesis recorded in tests. Leave JVM memory headroom for native memory/KCL buffers. No high availability claim: task replacement, deployments, and downstream faults can interrupt processing.

One internet-facing Application Load Balancer provides TLS termination and path routing to two target groups. POST `/api/v1/events` goes to Ingestion Service; GET analytics paths and `/api/v1/events/recent` go to Analytics Service. Default listener action denies access. Health checks reach readiness directly through target groups; public listeners do not route `/actuator/*`. One ALB is justified by TLS and two service routes, not by a need for a gateway service.

For controlled personal experiments, place tasks in public subnets with assigned public IPs and an internet gateway; task security groups accept application-port traffic **only from the ALB security group**. No SSH port. This permits ECR pulls and AWS API access without a NAT gateway. Public IPs still cost money and a security-group mistake can expose a task. Private subnets with NAT or interface endpoints provide another boundary but add cost; reconsider for a persistent shared deployment. [AWS Fargate networking](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html)

Use two public subnets in different availability zones for the ALB; this does not imply redundant single-task services. ALB ingress 443 is limited to the owner's current IP and explicitly allowed load-test source CIDRs. Require a user-controlled domain and ACM certificate for the eventual HTTPS API. These deployment inputs do not block local implementation. Do not open anonymous ingestion to the internet. Load generation from a changing/unapproved source requires an intentional network-rule update.

Host built React assets in a private S3 bucket behind CloudFront using origin access control; block public S3 access. CloudFront serves static assets only, not API proxy traffic. The browser calls the HTTPS ALB API directly, so the source IP allowlist remains effective. Static UI can be public and contains no embedded secrets or data. Configure CORS for the exact CloudFront origin. Cache fingerprinted assets, give index.html a short cache policy, and set frontend headers from the security specification. No ECS frontend task.

## Identity and configuration

An ECS execution role permits ECR pulls and CloudWatch log delivery; it is separate from task roles. Ingestion task role can write only its stream and perform the stream metadata calls needed by readiness. Analytics task role can read/describe/list shards on that stream, use required application-table item/query/transaction actions, manage the specific KCL metadata tables, and publish metrics in the chosen namespace. It cannot publish commerce events. Neither role provisions arbitrary infrastructure. Deployment tooling creates resources/TTL/IAM; inspect KCL's required actions against precreated tables during the AWS smoke test. Scope any unavoidable wildcard action with supported conditions and document why. SDK credentials come from the ECS task role provider, not environment access keys.

Non-secret configuration comes from task definitions. Future actual secrets belong in managed secret storage, but no secret service is needed just to hold table names. Frontend configuration is public; API URLs are safe, tokens are not. Logs redact unsafe configuration. Use normal SDK providers on developer machines and short-lived federated/OIDC credentials in future CI deployment workflows.

## Cost and lifecycle

Deploy only for bounded experiments, then tear down. ECS tasks, ALB hours/capacity, public IPv4, Kinesis shards/retention, DynamoDB transactional capacity/storage (including KCL tables), ECR images, CloudWatch metrics/log ingestion, S3, and CloudFront can all generate charges when the dashboard is idle. No fixed dollar estimate is asserted here. Check regional prices and quotas before deployment.

Set budget alerts before tests, but recognize alerts are not spending caps. Bound generator rate/duration, ECS maximum task counts (initial cap two per service), initial shard count, request admission, and DynamoDB capacity limits. Scale manually during early benchmarks so configuration stays attributable. Set seven-day log retention, retain only a small number of ECR images, and avoid per-event success logs at load. Teardown must inventory ALB, ECS tasks, stream, all six DynamoDB tables, log groups, images, S3/CloudFront, and any certificates/DNS resources created for the experiment. Removing tasks alone is insufficient. Retain a benchmark report/manifest before explicitly deleting its dataset.

The idle fallback failure was reproduced against the pinned KCL release: its [assignment calculation](https://github.com/awslabs/amazon-kinesis-client/blob/v3.4.3/amazon-kinesis-client/src/main/java/software/amazon/kinesis/coordinator/assignment/LeaseAssignmentManager.java) divides assigned throughput by the fleet target, which can both be zero. This local configuration correction changes metric selection, not stream delivery or application transaction semantics.
